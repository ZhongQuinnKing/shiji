# 验证状态（这份技能包被验到什么程度）

这份文件如实记录拾级做过哪些验证、验出了什么、改了什么——以及哪些没验过。
一个题库说自己"答案都是对的"，最有用的不是这句宣称，是它敢把验证账本摊开。

## 一、跑过的验证

### 1. 隔离验证（18 题，2026-10-08）

目前最严格的一次。口径：只给技能包、不给答案纸——作答者拿内核与篇目逐题答，
答完封存，再打开 `自测题.md` 对照每题"合格的样子"评分。每题记三样：
路由到哪一篇、回答要点、实际动作（读没读、搜没搜、搜了什么词）。

结果：机制是活的。政策时效类题真去搜了，方法类题没有为搜而搜，用户报姓名要求
检索时零检索——写在纸上的规则，真跑起来也这么动。抓出两处判据缝隙
（"篇末刚核验过≠免搜"、"要问就问全"），已补进规则。

### 2. 跨平台验证第一弹（Claude 侧，2026-10-08）

同一批题换一个平台跑，出 4 处规则歧义 + 4 处内容缺口，逐条修完（细节见 CHANGELOG v1.3.1）。

这次验证自己交代了一个方法问题，我们照登：先读了"合格的样子"再作答，
"知道评判标准再答题"会抬高分数——那份报告的通过率只能当乐观上限看。
下一轮换了顺序：先答完、封存，再对答案。

### 3. 真实使用撞出的第一处（2026-10-08，豆包端实测）

一位用户在豆包里装拾级做题，撞出真问题：考研报名篇写的是旧流程，2027 年起
官方已改为"报名与确认一体化"。双源机制按实时信息答对了，反馈回流后两篇
按官宣重写、加"最后核验"标注。这是"定弦"闭环第一次完整跑通——真实使用
撞出的缺口，吸收回库。

### 4. 逐篇事实核查与深度审校（2026-10-08）

两轮核查覆盖新写 46 篇与存量 105 篇，揪出 18 处实错，全改完。最高频的错型是
"把限定条件写成通例"——把某一类人的适用条件写成了所有人的门槛。深度审校
两轮另出缺口若干（逐条补齐，数字与条目见 CHANGELOG 与仓库内的审校台账），
抓出的四种"同一种浅"也已按线整改。

### 5. 工程门禁（每次推送自动跑）

- `scripts/check_content.py`：必需文件、交叉引用断链、AI 腔、占位符、红线短语、frontmatter
- `scripts/check_typos.py`：七类文字校对扫描（提醒式）
- `scripts/check_links.py`：对外文档里的 http 链接死链探测（提醒式）

## 二、没验过的（同样如实）

- **没有第三方独立验证**。以上全部是自测性质：要么项目自己跑，要么由 AI 平台
  在受控口径下跑。至今没有独立于项目的第三方评审或实测记录。
- **18 道题是抽样，不是全集**。151 篇的知识面远大于 18 题的覆盖面；题目考的是
  机制（路由、红线、双源回答、定弦、回答方式），不是逐篇抽查。
- **没有规模化用户数据**。这个项目很新，还没有一批真实用户的长期使用记录。

## 三、怎么自己验（欢迎复跑）

1. 装好拾级（见 `安装指南.md`）
2. **先答后对**：只把 SKILL.md 与 references 交给它，用 `自测题.md` 里的题去问；
   在这之前不要给它看每题下面的"合格的样子"
3. 对照评分。发现问题提 issue（"内容反馈"模板），我们核实后照改
4. 复跑结果如实归档——不管通过率高低

哪天有人做了独立验证，不管是夸是骂，只要愿意公开方法和结果，我们都记在这里。
